## 0. 摘要

**一句话结论**：这是一套**分层清晰、工程意识良好**的代码（可注入后端、令牌化主题、回调式进度、UI 与业务解耦），但它最核心的卖点——**「先复制并校验，全部一致后才删除源目录」**——在实现上**不成立**：校验只做"目标 vs 目标"的自比对，且对枚举遗漏完全无感。因此本工具目前存在**可复现的数据丢失路径**，不建议在包含空目录/符号链接/大量文件的真实用户目录上直接使用。

| 等级 | 数量 | 含义 |
|---|---|---|
| **P0** | 4 | 数据丢失 / 一致性事故，必须修 |
| **P1** | 6 | 严重缺陷，影响正确性或可用性 |
| **P2** | 23 | 一般缺陷，稳健性/可维护性/工程化 |
| **P3** | 8 | 建议项，清理与体验 |

**最需先修的三件事**
1. **P0-1 / P0-2**：把校验从"目标自比对"改为"**源 ↔ 目标**全量对照"（文件集合 + 目录集合 + 内容/元数据），否则删源这一步永远不安全。
2. **P0-4**：调整事务顺序为「复制 → 校验 → **写注册表** → 删源」，并引入可恢复的意图日志。
3. **P0-3**：把窗口关闭（X）接入 `_on_exit`，让"停止/退出"的承诺真正生效。

**动态验证的净效果**：3 条由初步探索提出的"疑似 P1"被实测**推翻或大幅修正**（见 §4 与 §3 的「修正说明」），说明本报告的结论均以可复现证据为准。

## 2. 总体评价

### 2.1 做得对、应保留的部分（正面确认）

- **无命令注入面**：所有 `subprocess` 均为列表形式（`shell.py:96-101`、`:141-146`、`:154-156`、`:244`），无 `shell=True`。
- **无裸 `except:`、无可变默认参数**：`copy_merge(..., skip_names: Sequence[str] = ())` 用的是元组（`fsops.py:278`）。
- **子串误判已被规避**：`is_within()`（`fsops.py:105-112`）用 `parent.rstrip("\\") + "\\"` 做前缀判断，`"D:\AB"` 不会误判为位于 `"D:\A"` 之内。
- **删除前置守卫**：`safe_remove_directory()` 先判 `isdir` 再 `rmtree`（`fsops.py:358-368`），拒绝删除非目录对象。
- **同盘走原子重命名**：`try_atomic_move()`（`fsops.py:371-384`）在目标不存在且同卷时 `os.rename`，无中间态。
- **注册表快照机制**：改动前落 JSON 快照（`transfer.py:301-314`、`registry.py:214-253`），提供回滚基础。
- **可注入注册表后端**：`MemoryBackend` / `Protocol`（`registry.py:36-124`）使核心流程可在不碰真实注册表的前提下测试。
- **单位一致**：空间与统计全程以**字节**为单位，无 KB/MB 混用。
- **图标引用管理正确**：`IconFactory._cache` 持引用（`icons.py:135-143`），`PhotoImage` 不会被 GC 掉图。
- **规范化的设计令牌**：`theme.px()` 覆盖全部 1px 线、间距与尺寸；界面代码基本无字面值。

### 2.2 核心安全假设是否成立

| 承诺（README / 界面文案） | 实现是否成立 | 证据 |
|---|---|---|
| "先复制并校验，全部一致后才删除源" | **不成立** | P0-1、P0-2 |
| "对比文件数与总字节数，两者一致才算成功" | **不成立**（比的是目标自己的数） | P0-1 |
| "任何一步失败会自动回滚" | 部分成立（仅注册表写入失败时回滚，且对 merge 场景有副作用） | P0-4、P2-12 |
| "未完成项目的源文件不会被删除" | **在点 X 关窗时不成立** | P0-3 |
| "同盘直接 `os.replace`" | 文档失真（实为 `os.rename`） | P3-4 |

## 3. 问题清单

### P0 —— 数据丢失 / 一致性（4 项）

---

#### P0-1　校验是「目标 vs 目标」自比对，从不与源比对

**位置**：`docmover/fsops.py:315-317`（记录）↔ `docmover/fsops.py:341-345`（校验）

```python
# fsops.py:315-317  copy_merge —— 记录的是【目标】文件的大小
shutil.copy2(full, target)
size = os.path.getsize(target)          # ← target
result.manifest[rel] = size

# fsops.py:341-345  verify_manifest —— 又是【目标】文件的大小
actual = os.path.getsize(target)        # ← 同一个 target
if actual != expected:                  # expected 也来自 target
    mismatched.append(...)
```

**现象**：`manifest[rel]` 存的是复制完成后**目标文件**的大小；校验时再对**同一个目标文件**取大小与清单比较。**源的大小、内容、时间戳从未参与比对**。只要 `copy2` 未抛异常，校验就恒为通过。

**动态验证（V1，已复现）**：

```
复制后           源 sha=44f8354494a5  目标 sha=44f8354494a5  大小=1000
篡改目标后       源 sha=44f8354494a5  目标 sha=7e33ae3f1e88  大小=1000
verify_manifest -> ok=True  detail='已校验 2 个文件'
```

**影响**：源与目标内容已经不同（大小恰好相同），校验依然判"通过"，随后 `transfer.py:434` 删除源目录 → **静默数据丢失**。现有单测 `test_core.py:168-179`（`test_verify_detects_missing_and_truncated`）用的是**手工构造**的 manifest（`{"keep.txt": 3, "short.txt": 99, "gone.txt": 1}`），从未验证"源 ↔ 目标"这一对，因此给了虚假信心。

**修复建议**：
1. 复制时记录**源**的 `(size, mtime)`，或对大文件做流式哈希（`hashlib.file_digest` / 分块 `blake2b`）；
2. 校验时**同时对源与目标复算并比对**；
3. 删源前做一次「源枚举集合 == 目标清单集合」的全量对照（文件集合 + 目录集合）。

#### P0-2　枚举与结构遗漏对校验不可见，却照样删除源目录

**位置**：
- `fsops.py:264`（`_iter_source_files`）、`fsops.py:228`（`scan_tree`）：`os.walk(root, followlinks=False)`，**未传 `onerror`** → 无法列目录时静默跳过整棵子树；
- `fsops.py:304-306`：只对**文件的父目录**执行 `makedirs` → **空目录永远不复制**；
- `fsops.py:312-314`：`os.path.islink(full)` → 记入 `skipped` 后 `continue`（不复制）；
- `fsops.py:335`：`verify_manifest` **只遍历 manifest**；
- `transfer.py:434`：校验通过即 `safe_remove_directory(item.current)` 删源。

```python
# fsops.py:304-306  空目录不会被建立
target = os.path.join(dst, rel)                    # rel 来自文件列表
os.makedirs(os.path.dirname(target), exist_ok=True)

# fsops.py:335  verify_manifest 的遍历范围就是 manifest 本身
for rel, expected in manifest.items():
```

**动态验证（V2，已复现两组）**：

```
[V2a 空目录] 源含空目录 empty_sub；复制后目标存在该目录？ False
[V2a 空目录] verify_manifest -> ok=True detail='已校验 1 个文件'
[V2a 空目录] 删源 -> removed=True；源目录已不存在？ True
[V2a 结论] 空目录既未复制、又未阻止校验、源已删 -> ✔ 复现结构丢失

[V2b] 复制完成，清单含 ['p.txt', 'q.txt']
[V2b] 从清单移除 q.txt 后 verify_manifest -> ok=True detail='已校验 1 个文件'
[V2b] 删源 -> removed=True；源仍存在？ False
[V2b 结论] 校验对『源里有、清单里没有』的文件完全无感 -> ✔ 复现数据丢失路径
```

**影响**：任何"源里有、但没进清单"的东西——空目录、符号链接、因权限/超长路径被 `os.walk` 静默漏列的子树——都不会触发校验失败，随后源目录被整体删除。**这是与 P0-1 同源、但更直接的丢数据路径。**

**修复建议**：
- 复制前**显式重建全部目录**（含空目录）；
- 符号链接/junction 需明确策略（跟随复制 / 原样重建链接 / 明确跳过并**阻止删源**并告警），不得"静默丢弃后删源"；
- 为 `os.walk` 传 `onerror`，一旦发生即令该项整体失败（不删源）；
- 删源前做「源完整清点 vs 目标清单」的差集校验，非空即拒绝删除。

#### P0-3　窗口关闭（X）未接入优雅退出：绕过确认与取消，后台线程被强杀

**位置**：`docmover/ui/main_window.py:289`（`_on_exit` 只绑在按钮上）、`:837`（工作线程 `daemon=True`）、`:1031-1042`（`_on_exit` 的确认逻辑）

> **修正说明（动态验证推翻了我的初始假设）**：最初的探索结论是"未绑定 `WM_DELETE_WINDOW`"。实测（V4）表明 **Tk 默认就已把 `WM_DELETE_WINDOW` 绑到 `destroy`**：
> ```
> root.protocol('WM_DELETE_WINDOW') -> '1900282704448destroy'
> bare Tk -> '1897285022464destroy'      # 裸 Tk 同样如此（Tk 内置默认）
> ```
> 因此准确的问题描述**不是"没绑定"，而是"没有重定向到 `_on_exit`"**：全仓搜索无任何 `root.protocol(...)` 调用。

```python
# main_window.py:1031-1042  这段精心写的确认逻辑，只有点「退出程序」按钮才会执行
def _on_exit(self) -> None:
    if self._busy:
        if not messagebox.askyesno("正在执行", "……仍然直接退出程序吗？"):
            return
        self._cancel.set()
    self.root.destroy()

# main_window.py:837  工作线程是 daemon：mainloop 一返回就被强杀
threading.Thread(target=worker, args=args, daemon=True).start()
```

**现象**：点击窗口右上角 X → 走 Tk 默认 `destroy()` → `mainloop` 返回 → `run.py` 的 `_cmd_gui` 返回 → 进程退出 → **daemon 工作线程在任意时刻被强杀**。

**影响**：若此时线程正停在 `safe_remove_directory`（`rmtree` 非原子）中间，源目录会**被部分删除**，而注册表**尚未写入**——资源管理器仍指向那个残缺目录，目标的完整副本却在 `D:\UserData` 下无人知晓。这与 `_on_exit` 弹窗里"未完成项目的源文件不会被删除"的**明确承诺直接矛盾**，且没有任何预警。

**修复建议**：
1. `root.protocol("WM_DELETE_WINDOW", self._on_exit)`，让 X 与按钮走同一路径；
2. 工作线程改非 daemon，或在退出前 `join`（配合 `_cancel` 与超时兜底）；
3. 退出时输出"正在安全收尾…"状态，避免用户以为程序卡死。

#### P0-4　删除源目录发生在写注册表之前，且中断后无恢复机制

**位置**：`docmover/transfer.py:434`（删源）先于 `:449`（写注册表）

```python
# transfer.py:434-446
removed, remove_message = fsops.safe_remove_directory(item.current)   # ← 先删源
...
moved = True

# transfer.py:448-449
ok, message, written = self._write_registry(item, self._registry_payload(item))  # ← 后写注册表
```

**现象**：每项的顺序是「复制 → 校验 → **删源** → 写注册表」。设计意图是靠 `_rollback_move()`（`:467`）在注册表写入失败时把目录搬回来，但**进程被杀 / 断电 / 崩溃**这一情形完全没有覆盖：没有任何持久化的"未完成事务"标记，启动时也不做状态恢复。

**影响**：在删源成功、注册表写入之前被终止 → 源目录已不存在，而 `HKCU\...\User Shell Folders` 仍指向那个已消失的旧路径。重启后 `resolve_current()` 读到的仍是旧路径，用户看到「文档/桌面」为空——数据其实在目标盘，但系统和用户都"找不到"。

**修复建议**：
1. 顺序改为「复制 → 校验 → **先写注册表指向已校验的目标** → 再删源」；
2. 引入事务/意图日志（如 `intent.json`：源、目标、阶段），启动时检测未完成事务并恢复或提示；
3. 快照（`backups\registry-*.json`）目前只落盘不自动应用，建议在检测到孤儿状态时提示一键回滚。

```python
    return f"目标磁盘空间不足：..."

# fsops.py:136-139  取不到时返回 0，被当成"无需检查"而不是"未知"
    try:
        return shutil.disk_usage(probe).free
    except OSError:
        return 0

# fsops.py:235-238  统计时静默吞掉 OSError → needed 偏低
            try:
                stat.bytes += os.path.getsize(full)
            except OSError:
                pass
```

**影响**：
1. `free_space` 失败（网络盘抖动、权限、竞态）返回 `0` → 条件短路 → **空间不足或未知时反而不阻断**，一路复制到写满；
2. `needed` 来自 `scan_tree`，而它对 `getsize` 的 `OSError` 静默 `pass`、不计 junction 内容 → **系统性低估**；
3. 未预留簇大小/元数据/临时开销，复制期间源与目标并存，实际占用 ≈ `needed`。

**修复建议**：`free_space` 返回 `Optional[int]` 区分"未知"与"0"；空间不足**或未知**都阻断并给出明确提示；估算加安全系数（如 ×1.1 + 固定余量）。

### 第四批（同日）：「恢复系统默认值」与早期版本行为对齐 + 补一道高危闸门

**起因**：产品负责人发现两版「恢复系统默认值」行为不一致——早期版本会**真搬文件**，本版
只改注册表。遂逐条核对其实现并结合本机实测后，决定对齐并加固。

**早期版本的真实动作（实证，非推测）**：其对「恢复默认」项按固定顺序依次执行：

```
整目录复制（当前 → 默认，覆盖）→ 短延时 → 递归删除当前目录 → 写注册表 ×2
→ (Win7+) 删除旧别名键 → 给目标根设 System 属性 → 结束 explorer.exe 进程
```

**早期版本缺陷**：整目录复制后**不看返回码**就递归删源 —— 复制失败（空间不足/被占用）
也会删源。

**本版改造（产品决策：固定为完整恢复；空间不足阻断该项并报缺口）**：

| 项 | 做法 |
|---|---|
| 执行体 | `restore_defaults` → `build_restore_plan` + **复用 `execute()`**，天然继承「复制 → 源↔目标全量校验 → 写注册表 → 校验通过才删源」 |
| 空间 | 按项 `blocking_reason()` 闸门（5% + 64 MB 余量），**只阻断该项**、报出缺口，其余项照常 |
| 源不存在 | 降级为 `registry_only` → 仅修正注册表、不动文件（早期版本此处整项跳过，注册表永远修不回来） |
| 死字段 | 不支持 Win7，删除全库无人使用的 `FolderSpec.legacy_default` |
| UI | 确认框如实描述「注册表 + 文件搬回」；去掉「文件未搬动」暗示；按钮 ToolTip 同步 |

**⚠️ 本轮自查独立发现并修复的一项高危缺口（§6 未列）**：
`build_restore_plan` 有意**不**调用 `validate_destination`（默认目标位于 `C:\Users\<用户>` 下，
而那正是转移路径的禁区），但**因此一并丢掉了 `validate_destination` 里最关键的
「源与目标互为祖先/后代」互斥检查**。后果：若注册表把 `Personal` 指向用户配置根
`C:\Users\<用户>`（或其父目录），恢复会把整份用户配置**自我嵌套复制**进 `…\Documents`，
校验通过后再**删掉整个用户配置**。已修复：`_unsafe_restore_source(path, target)` 增加
嵌套互斥判断，并在 `build_restore_plan` 传入 `target` 接线。

**验证**：新增 2 条用例（闸门单元 + 端到端接线），测试 **147 → 149 全绿**，门禁 6/6；
两处突变（M1 删掉嵌套判断、M2 调用点丢掉 `target`）**均 RED**，字节级还原后 md5 一致。

**一次事故与加固（如实登记）**：端到端用例最初用**真实 `%USERPROFILE%`** 推导父目录，
突变 M1 生效后闸门失效 → 触发对**整份用户配置**的递归扫描，进程被强杀、
`finally` 未执行 → 源码残留 `if False:  # MUTATED`（已立即发现并从内存原文还原，复核
`MUTATED=0`、`CRLF=0`）。加固：① 该用例改为用**临时目录**构造 spec（闸门坏了也只会扫一个
小目录）；② 突变脚本增加「先备份原文 + `subprocess` 超时兜底 + 还原后 md5 双向核对」。

#### ③ chevron 二次缩放缺陷的发现与修复（本轮最有价值的一条）

`_install_combobox_chevron` 原写：

```python
self._icons.chevron_down(units=self.px(12), color=_hex2rgb(c))
```

而 `icons.IconFactory._make` 内部是 `size = max(12, round(units * self.scale))`——
`units` 是「16 单位画板」的**设计单位**，内部已按 scale 缩放。外层再套一层 `px()` 就是**二次缩放**：

- **100% DPI**：`px(12)=12`，内部 `round(12×1.0)=12`——凑巧等于设计值，此前一直看不到问题；
- **150% DPI**：`px(12)=18`，内部 `round(18×1.5)=27`——实际渲染 **27px** 的箭头，
  与设计意图（12 物理 px）差一倍多。

修复：`units=12`（去掉 `px()`），并在该处注释说明口径。

**同类核查（逐个确认口径，均正确、不改）**：

| 调用点 | 写法 | 结论 |
|---|---|---|
| `dialogs.py` 弹窗图标 | `IconFactory(self.tl, _scale_of(parent)).status(kind, units=44)` | 正确：`units=44` 是设计单位，工厂 scale 即 `_scale_of(parent)`，内部缩放一次到位 |
| `main_window.py` AdminBanner | `self.theme.icon("warning", units=16)` | 正确：`Theme.icon` → `self._icons.status(units=…)`，`Theme._icons` 的 scale 与 `Theme.scale` 同源 |
| `theme.py` `Theme.icon(kind, units=16)` 默认值 | 设计单位，正确 |
| `theme.py` `checkbox(...)`（未传 units，默认 16） | 设计单位，正确 |

单位口径已写入 `docs/ui-skeleton.md` §5：「图标 `units` 一律是设计单位，不得再过 `px()`」。

#### ① 第二个实例的提示窗「显示空白」——根因与修复

用户报告：已开一个实例后再启动一个，第二个实例的弹窗错误、显示空白。

**根因（实测确认）**：`run.py::_cmd_gui` 原顺序为 `_enable_dpi_awareness()` →
`root = tk.Tk()` → 单实例判定 → `tkinter.messagebox.showinfo(...)`。`tk.Tk()`
建出的根窗口**从未进入事件循环**（没有 `update` 也没有 `mainloop`），尚未
realize/映射；而原生 MessageBox 需要一个已就绪的 owner HWND 才能正常绘制。
owner 未就绪的模态框在 Windows 上整块不绘制——即用户看到的空白。

**连带实测出一条硬约束**（决定修法）：Tk 的 `wm transient` 规定 **master 未映射时，
设了 transient 的子窗口永远不会被映射**。实测（根窗口 `withdraw()` 后建 Toplevel）：

| 是否设 transient | `winfo_ismapped()` | `winfo_viewable()` |
| --- | --- | --- |
| 设 | 0 | 0 |
| 不设 | 1 | 1 |

即「隐藏根窗口后照旧弹窗」会把问题从「弹窗空白」恶化成「弹窗完全不出现」，
必须一并处理。

**修复（三处）**：

| 文件 | 改动 |
| --- | --- |
| `docmover/ui/dialogs.py` | `ModalDialog.__init__` 新增 `transient: bool = True`；仅当 `transient` 为真**且父窗口已映射**时才调用 `self.tl.transient(...)`。`_center_on_parent` 增加退化分支：`pw <= 1 or ph <= 1 or not 父窗口已映射` 时改为**按屏幕居中**（`x=(sw-w)//2`、`y=(sh-h)//3`），避免贴角/出屏。模块 docstring 记录该约束 |
| `run.py` 新增 `_notify_already_running()` | 单实例提示改为自绘弹窗：`tk.Tk()` → `withdraw()` → `dialogs.show_info(root, APP_TITLE, "程序已在运行。请勿重复打开。")` → `finally: root.destroy()`。自绘弹窗自身抛异常时退回原生 messagebox，保证「已运行」信息一定送达 |
| `run.py::_cmd_gui` | 单实例判定从「`tk.Tk()` 之后」前移到「`tk.Tk()` **之前**」，分支内先 `logger.info(...)` 再 `return _notify_already_running()`——第二个实例不再创建主界面。启动失败分支的 `messagebox.showerror` 同类问题一并改为 `dialogs.show_error(root, ...)`，原生保留为 except 兜底 |

### §8.9 第九批：修复「确认弹窗说好的浅蓝高亮从未出现」（2026-10-14）

**现象**：用户截图指出「确认开始转移」弹窗里写着

1. 功能链路本身是通的：`main_window._on_start_transfer` 会先

3. **红/绿双色实验钉死规则**：ttk 标签冲突时，**先 `tag_configure` 的赢**，

#### 与早期版本对照：Desktop.ini 是**有意不做**，不是「早期版本也没有」

早期版本**确实会写** `Desktop.ini`：

```
在目标根目录那一级写入 Desktop.ini：
  LocalizedResourceName = <界面上的「个性化目录别名」，默认「用户目录」>
  IconResource          = %SystemRoot%\system32\imageres.dll,169
  并把该 ini 置为 Hidden+System
```

本工具 `shell.write_desktop_ini()` **生产链路从未调用**（`README.md` 已同步改为「预留接口」）。可见后果：被转移的**目标根目录**（`D:\UserData`）显示其物理名而非中文别名——早期版本会在该层写 `Desktop.ini` 把它显示成「用户目录」，本工具不写，故显示 `UserData`。至于各文件夹层（`Documents` ↔「文档」）的本地化，则由早期版本与本工具都整树复制带走的 **Windows 自带** `Documents\desktop.ini` 承担，**两者行为相同、无差异**（更精确的层级归因见 §8.13）。

**已决策：不做**，理由：①它会给目标根**加 Read-only 且没有还原路径**（「恢复默认」只回滚注册表与搬回文件，不碰属性、不删 ini），接入前必须先设计属性还原；②写入层级需产品决策（目标根 / 用户目录 / 各文件夹三级的显示效果与属性波及范围不同）；③早期版本该行为与目录生命周期耦合（给根设 System 属性、空根自动删除），只照搬"写三行 ini"不等于完整对齐。更正的层级分析见 §8.13（此处较早的一稿曾把「文件夹层」误归因为 Desktop.ini 的作用点）。

#### 两条值得记下的知识

* **门禁红线曾是字节级子串判定**：早期实现里有一条红线守卫，对 `docmover/**` + `run.py` 做朴素 `in` 判定，**会命中注释与 docstring**。这是有意的项目不变量（运行时代码不得以任何形式残留早期版本名）；朴素判定换来的确定性比精确性更值钱。该守卫已随早期版本名一并移除（见 §8.16），但留下的教训仍然成立：**出处类信息应写进 `docs/`，运行时代码只留不带具体来源文件的指引**。
* **「测试全绿」不能证明守卫接线了**：R8 的守卫有 4 条测试、全绿，但生产代码零调用。测试直接调函数，绕过了接线。发现这类缺口靠的是「对每个新守卫 grep 它的生产调用点」——本轮已把该检查纳入交叉复核的固定口径。

### §8.12 第十二批：单实例提示窗图标语义（2026-10-15，用户反馈驱动）

**现象**：重复打开时提示窗的感叹号是**蓝色**的，其他弹窗都是**棕色**。

**修复**：`run.py` 自绘弹窗改 `show_warning`，并**顺手修正原生兜底分支**（`messagebox.showinfo` → `showwarning`，同一语义、之前漏改）；加注释写明图标语义约定，防止后人再按"这只是个提示"改回去。

**护栏**：`tests/test_entrypoints.py::TestAlreadyRunningPopup` 2 条——
① 自绘弹窗走 `show_warning` 且 `show_info` **从未被调用**、文案含「已在运行 / 请勿重复打开」；

## §8.13 第十三次：Desktop.ini 归因纠正（文档纠错，无代码改动）

**起因**：用户要求详细解释 Desktop.ini 这一块（"这一块我没太懂"）。解释前先取证，结果**推翻了我自己上一轮写进 README 与记忆的归因**。

**早期版本的事实（取证）**

| 证据 | 位置 | 说明 |
|---|---|---|
| 写入点 | 早期版本源码（目标根那一级） | 直接在目标根下写 `Desktop.ini` |
| 目标根变量 | 早期版本源码 | 推荐值 `D:\UserData`（**目标根**）；文件夹路径＝目标根 + 用户名 + 基名 |
| 别名来源 | 早期版本界面 | 「个性化目录别名」输入框（默认「用户目录」） |
| **动机的铁证** | 早期版本界面提示语 | 「目标路径只支持一级文件夹」「**只支持英文和数字**，前端默认显示中文『用户目录』，可在配置文件中个性化」 |
| 幂等 | 早期版本源码 | 先读后比，一致则跳过（避免反复动属性） |
| 执行时机 | 早期版本源码 | ini 写入不在条件分支内——「未勾选或路径相同」时**也会写** |
| 耦合行为 | 早期版本源码 | 另给目标根设 System 属性；并在「根下只剩 Desktop.ini」时删掉整个根目录 |

**结论**：早期版本写 ini 是**为了让目标根目录显示成中文别名**（物理名强制 ASCII → 显示名换中文），
**不是**为了让 `Documents` 显示成「文档」。

**先前的错误归因**：README「已知边界」原写「转移到目标盘后，文件夹在资源管理器里显示物理名
（如 `Documents`）而非本地化名（如「文档」）……早期版本会在目标位置写 `Desktop.ini`」——
把**文件夹层的本地化**错记到**目标根层的 ini** 头上。实际 `Documents` ↔「文档」由 Windows
自带的 `Documents\desktop.ini`（`LocalizedResourceName=@%SystemRoot%\system32\shell32.dll,-21770`）
承担；`fsops.copy_merge` 不按属性过滤文件（只处理重解析点与稀疏文件），该文件随目录整树
复制被带走——**两者在这一层行为相同，不存在差异**。

**本机实测**（`D:\UserData`，Windows 11）

```
D:\UserData                      属性=D         无 Desktop.ini  ← 早期版本若跑过应有 ini + System 属性
D:\UserData\me                   属性=D         无 Desktop.ini
D:\UserData\me\文档              属性=R+D       Desktop.ini 属性=H+S
  └ 内容：LocalizedResourceName=@%SystemRoot%\system32\shell32.dll,-21770
          IconResource=%SystemRoot%\system32\imageres.dll,-112
C:\Users\me\Documents            属性=D         无 Desktop.ini（随目录迁走了）
```
内容为 **shell32 资源引用格式**，与早期版本写的**字面别名 + `imageres.dll,169`** 格式完全不同
→ 该 ini 既不来自早期版本、也不来自本工具（`write_desktop_ini` 生产零调用），而是 Windows
自带并随目录一起被搬走的。

**处置**：仅改文档（无代码改动），把归因写对并把两层差异分开：
1. `pydm/README.md` 已知边界：该 bullet 重写为「**目标根目录不会显示为中文别名**」，
   写明早期版本动机（ASCII 物理名 + 中文显示名）、本工具此处显示 `UserData`、不接的三条理由；
2. `pydm/README.md` 同处**新增一条**「别把上一项与文件夹的本地化显示混为一谈」；
3. `docmover/shell.py::write_desktop_ini` docstring：不接理由由「二」改「三」
   （① 属性副作用无还原路径 ② 写入层级需产品决策 ③ 与目录生命周期耦合），
   并补「不要用本函数解释文件夹显示英文物理名」的澄清段。

**结论（用户 2026-10-15 确认：不做）**：仍**不接线**。主因是**属性副作用没有还原路径**——`transfer.restore_defaults`
（`:1271`）→ `build_restore_plan` → `execute` 全程只回滚注册表与搬回文件，**不碰任何文件
属性、也不删 `Desktop.ini`**；次要因是写入层级需产品决策、且该行为与目录生命周期耦合。

**补正一处先前的措辞**：上一轮我以「与早期版本那个唯一的目标根写入点不同，照搬有
写错位置的风险」为由，**这一条其实站不住**——早期版本写入点就是目标根，本工具的 `dest_root`
同样是唯一的、明确定义的（`transfer.py:725`）。真正的阻塞项是属性还原，不是层级歧义。
层级只影响「写哪一级」，不构成风险。

**验证**：门禁 8 项全 `[OK]`、`Ran 237 tests in 114.973s OK`（仅文档改动，测试数不变）。

**教训（已写入技能）**：文档里的「差异归因」必须像代码一样取证——先读写入点所在
**变量**的定义，再读它**自己的提示语**；只看到"会写 ini"就推断"所以文件夹才显示中文"
会张冠李戴。举证顺序：**变量定义 → 提示语/注释 → 本机实测 → 才写结论**。

### 8.14.2 两项必须留给将来查证的事实

**事实一：`\\?\` 绕过当前「没造成删除」，靠的是一个与安检无关的偶然崩溃。**

审计发现，第 3 项（`\\?\` 绕过源禁区）之所以**当前没有真实删除过用户数据**，是因为
下游 `fsops.enumerate_source()` 里的 `os.path.relpath` 在**混合前缀**（一端带
`\\?\`、一端不带）下会抛 `ValueError`，而该异常被通用 `except` 兜住——
**安全性由一次意外崩溃兜底，而不是由安检逻辑兜底**。

> **行号取证说明**：审计原始记录写的是 `fsops.py:629`。本节成文时复核，该
> `relpath` 实际位于 `docmover/fsops.py` 的 `enumerate_source()` 内（当时落在
> 663 / 676 行两处）。**行号漂移的原因**是本轮放行修复中 `fsops.py` 正被并行修改。
> 故此处**按函数名取证而非按行号**——与本轮「文档不写会漂移的东西」同一口径。

推论（重要）：**任何人一旦"修好"那个 `relpath` 调用，这条就会从"崩溃中止"变成
"真实删除路径"**。因此改动 `enumerate_source()` 时**必须同时**补齐源禁区对
`\\?\` 前缀的归一化判定，否则等于把一个未爆的雷改成引爆。这类「靠运气安全」必须
显式记录在案，不能被后来者当成"没问题"。

**事实二：`shell.restart_explorer` 里的 `taskkill /f /im explorer.exe` 在生产中永远执行不到。**

原因是 `is_autorestart_shell_enabled` 读的是 **HKCU**，而该值实际位于 **HKLM**，
判定恒为假 → 强杀分支不可达。属**「已上膛、保险未开」**状态：代码写着强杀，
但当前走不到。**本轮只做加固、不改可达性**——刻意不去"修好"它（一旦可达，
就会对用户的资源管理器执行 `/f` 强杀，收益不明确而风险明确）。将来若要动它，
必须连同「是否应该强杀」这个产品决策一起评审。

> **取证**：`docmover/shell.py::is_autorestart_shell_enabled` 的 docstring（审计 F7，
> 标注「勿改」）已把该口径与「已上膛、保险未开」的结论写在函数上；
> `restart_explorer` 的 `taskkill` 实参在 242 行附近。本节与代码自述一致。

### 8.15.8 教训

- **「下限」断言挡不住漂移**：`MIN_PYTHON=(3,10)` 让 3.13 顺利通过、打出与「内嵌 3.14」
  声明矛盾的产物——**只要有正例能溜过，断言就等于没有**。修法不是「把下限抬高」，而是
  「**精确等于唯一真源**」（D3 由下限 → 强断言）。
- **单一真源要真的被引用**：`EXPECTED_PYTHON`、`pyinstaller==…` 若不被 `build.py` 读取，
  就只是文档里的数字。本轮把它们变成 `build.py` **实际的断言输入**（`import` / 解析 pin）。
- **文档必须与产物同轮对齐**：D1 的根因是「产物换了、文档没换」。凡「内嵌 X / 约 N MB /
  仅含某文件」这类**对产物事实的断言**，都要在**重打包的同一轮**里复核，否则下一次仍会漂移。
- **「不写会漂移的数字」是复发性缺陷（本轮复发）**：同一轮次内，README 的产物字节数就漂了
  **两次**（13,156,126 → 13,155,347）；而 QA 实测**构建本身不可字节复现**（同源码两次构建的
  字节数就不同）⇒ **任何写死的精确字节数都必然过期**。这正是 §8.14.4（写死 160 项 / 15 处
  弹窗）的**复发**——毕竟本轮起点 D1 就是「产物换了、文档没换」这一类。修法同 §8.14.4：
  把**每次构建都可能变**的量（产物尺寸）写成**不变量 / 量级**（`约 12.5 MB` + 「精确字节数
  以 build.py 输出为准」），精确值只在能自动同步处（产物元数据）出现。

### 8.16.1 只读下拉框聚焦后文字不可见（真实缺陷，已修）

**结论：不正常，是缺陷。** 已修复，并加了会红的回归锁。

**用户可见现象**：打开程序 → 点「目标根目录」下拉框 → 点空白处，下拉框里的路径
**整格消失**，看着像值被清空了——但 `get()` / `textvariable` 里的值其实一直都在。

**根因（实测定位，非推测）**：clam 主题的 `TCombobox` 把**文字色**挂在
`-selectforeground`（默认白）上，而该选项的映射只在 `!focus` 命中；下拉框一旦获得焦点
（"点开下拉再点空白处"正是让它在关闭后仍保持焦点的那条路径），文字色就回落到基值**白色**。
本主题此前又把**只读态底色**映射成 `surface`（白），于是**白字画在白底上**，整格不可见。
反过来，不映射只读底色的主题不会暴露它（只读底仍是深色，白字看得见）——所以这条缺陷
只会在"映射了只读底色"的主题里出现，肉眼截图（不聚焦时）也一切正常。

**修法**：**映射只读态底色，就必须同时映射只读态文字色**。`ui/theme.py` 的
`style.map("TCombobox", ...)` 补齐 `foreground=[("disabled", text_disabled), ("readonly", text)]`
（`disabled` 必须排在 `readonly` 之前——ttk 取首个命中项）。

**回归锁**：`tests/test_ui_smoke.py::test_readonly_combobox_maps_text_color_explicitly`
锁**样式表本身**（`style.map(...)` 的返回），而不是 `lookup`——`foreground` 已由
`configure` 给了基值，`lookup` 在缺映射时也会返回同一个值，对这条缺陷不敏感（会假绿）。

**在交付 exe 上的端到端复现（真实鼠标 + 像素判定）**：探针走用户那条原路径——
定位下拉框 → 真实点击打开下拉 → 真实点击空白处 → 截图统计下拉框内**深色像素数**：

| 时刻 | 下拉框内深色像素 | 已知空白区（零点参照） |
|---|---|---|
| 初始 | 209 | 0 |
| 点开下拉 → 点空白处后 | **209** | 0 |

两者完全一致 → 文字始终在，缺陷未复现；零点参照恒为 0 → 判据不是"恒为高值"。
（缺陷版用同一判据测得的读数是 **0**，即文字确实消失了。）存证截图：
`tools/shots/combo_box_after_click.png`（点击后的下拉框特写）、

## §8.19 第十九次：P2-2 落地——`AutoRestartShell` 判定改读 HKLM（2026-10-16）

承 §8.18 §5.2 第 8 项。该项是**产品决策**，作者选定 **A 方案：修成真正生效**。
本次改动是**行为变更**（首次真正启用 explorer 重启），故单独成节。

### 8.19.1 根因与硬证据

`is_autorestart_shell_enabled()` 读的是 `HKCU\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\AutoRestartShell`，
而该值的真值位置在 **HKLM**（Microsoft 文档：`REG_DWORD`，取值范围 `0|1`，**默认 1**）。
本机只读实测（`D:\tmp\regprobe_autorestart.py`，走 Python `winreg`；本机 `reg.exe` 被安全策略拉黑）：

| 位置 | 实测结果 |
|---|---|
| `HKLM\...\Winlogon\AutoRestartShell` | **`1`**（`REG_DWORD`） |
| `HKCU\...\Winlogon` 子键 | **存在但无该值**（只有 `RestartApps` / `ExcludeProfileDirs` / `BuildNumber` / `FirstLogon` / `ParseAutoexec`） |

故旧判定**恒为假** → `restart_explorer` 恒走「已跳过重启」→ `taskkill` 分支生产不可达。
界面问「是否重启资源管理器」，用户点「是」，拿到的却是「已跳过」——**读错 hive 的口径缺陷**，
而不是此前文档所称的「刻意保守」。§8.14.2「事实二」与 README「已知边界」的表述据此更正。

### 8.19.3 判定语义（三态 + 失败）

| HKLM `AutoRestartShell` | 判定 | 理由 |
|---|---|---|
| `=1` | 允许重启 | 系统会把 shell 拉回来 |
| **不存在** | 允许重启 | Windows **默认即为 1**（MS 文档）；缺省 ≠ 关闭 |
| `=0` | 跳过（并如实告知用户） | 管理员显式关闭了自动重启，尊重该设置 |
| 读取失败（权限/句柄/损坏） | 跳过 | **未知时不冒险**，fail-closed |

「值不存在按启用」是安全的，因为桌面恢复的**真正保险**是 `restart_explorer` 末尾那道兜底：
结束后复查进程，没回来就用 `ShellExecuteExW`（**不继承管理员令牌**）主动拉起。
`AutoRestartShell` 只是"系统自己会不会拉回来"这层**前提**判定。

### 8.19.4 伴随修复：强杀与列举同口径

`restart_explorer` 原先**只对 `taskkill` 加用户过滤，列举 explorer 不过滤**。
在「别人也登录着（RDP / 快速切换用户）」的机器上，"我们自己的 explorer 回来了没有"
会被**别人的** explorer 干扰 → 该兜底拉起时不拉、还误报「资源管理器已重启」。
该不一致只在路径放开后才**有实际后果**，故与本次一并修掉：`_user_filter()` 现在
计算一次，`taskkill` 的 `/fi` 与三处列举共用同一过滤。

核验 5 项（全部**只读、不运行 exe**，避免 UAC 提权与真实改注册表）：

| 项 | 断言内容 | 单一真源 |
|---|---|---|

### 8.23.2 一处**自引入**回归（已修）

脱敏脚本用 `Path.write_text()` 落盘，**Windows 下把 `\n` 转成了 `\r\n`**，直接触发红线「文本统一 LF」的隐患（工作区三文件被写成 CRLF）。修法：以**字节级 CRLF→LF 逆归一化**还原（脚本整文件重写，故可精确逆转）；三文件 CR 计数归零，全树复扫无 CR。

> 教训：Windows 上凡"读文本→写文本"的批处理脚本，**必须显式 `newline=""` / `newline="\n"`**，否则默认换行转换会破坏 LF 不变量。已记入本仓经验。

## §8.25 第二十五次：CI 恒红——控制台编码（2026-10-16）

**现象**：补上仓库根 `README.md`（含 CI 徽章）后，徽章显示 **failing**。查 Actions：两次运行（`main` / `v3.0.0`）**均失败**，其中 `main` 那次 **22 秒**即退出——说明在很早的步骤就挂了。

**定位**（`gh run view --log-failed`）：

```
File "pydm\tools\ci_check.py", line 285, in main
    print("== ci_check：本地门禁 ==")
UnicodeEncodeError: 'charmap' codec can't encode characters in position 11-15
```

**根因**：GitHub `windows-latest` runner 的控制台编码是 **cp1252**（不是 UTF-8），而门禁**第一行**就要打印中文标题。**纯环境问题，非产品缺陷**——本地（UTF-8 控制台）一直 8 项全绿，故表现为经典的「**CI 恒红但本地全绿**」。

**修法（双保险）**：

1. `tools/ci_check.py`：新增 `_force_utf8_output()`，**导入时**把 `stdout`/`stderr` `reconfigure` 为 UTF-8 + `errors="backslashreplace"`；流不支持 `reconfigure` 时**静默跳过**（退化为原行为，**不引入新的失败模式**）。
2. `.github/workflows/ci.yml`：job 级 `env: PYTHONUTF8=1 / PYTHONIOENCODING=utf-8`——顺带把 **unittest 子进程**的输出也钉成 UTF-8。

**验证**：本地以 `PYTHONIOENCODING=cp1252` **复现**原崩溃场景 → 修复后 **8 项全 [OK] / `Ran 329 tests OK`**。

**备注**：该问题**一直存在**，只是此前仓库根 README 缺失、徽章不可见，故未暴露；`ci_check.py` 原 docstring 已意识到「GBK 控制台无法编码 ✓/✗」，但没覆盖"中文正文本身"这一层。

**产物**：只改 `tools/` 与 CI 配置，**不进 exe**，**未重打包**。

**结论：CI 恢复绿色；问题属环境编码，与产品代码无关。**


## §8.26 第二十六次：CI 仍红——状态列下限随「数据宽度」漂移（2026-10-16）

**现象**：§8.25 修掉编码崩溃后，CI 依旧 **failing**，但这次跑满了全流程：

```
Ran 329 tests in 123.001s
FAILED (failures=1)
```

**定位**：门禁原先只在「失败」时打印一行摘要，看不到是哪条用例。先让 `check_tests()`
回传 unittest **原始输出**（`stderr + stdout`），`main()` 在失败时回显**末 80 行**
（§8.25 同批改进），才拿到真凶：

```
FAIL: test_status_column_fits_labels (tests.test_ui_smoke.TestMainWindowSmoke)
AssertionError: 64 not greater than or equal to 90
```

**根因**：这条用例除了「状态列 ≥ 内容需要宽度」这条**与字体无关**的契约外，还额外
断言了一个**绝对像素下限** `theme.px(90)`。而状态列的「内容需要宽度」取自**当前表格里
最长的那条状态文案**——它是**随数据漂移**的：

| | 开发机 | GitHub runner |
| --- | --- | --- |
| `D:\UserData\Administrator\Documents` | **存在**（本工具此前转移过） | **不存在** |
| 首行状态文案 | `将合并（0 个文件 / 0 B）` | `待转移` |
| 该文案宽度 | **170px** | **42px** |
| 状态列「内容需要宽度」 | **182px** | **57px** |
| 状态列实得宽度（修复前） | **182px** | **63px**（实测 64，差 1 为路径串微差） |

即：**同一份代码、同一套断言，只因表格里有没有一条长状态文案，列宽就从 182px 掉到
63px**。而 `90` 这个下限是在**开发机的数据**下「标定」出来的，换个数据集就不成立——
典型的「**本机绿、CI 红**」。

**排除字体因素**（一度误判为字体差异，实测否决）：逐候选字体量「待转移」的需要宽度，
`HarmonyOS Sans SC` / `Microsoft YaHei UI` / `Noto Sans SC` / `Segoe UI` / `Tahoma` /
`TkDefaultFont` **一律 54px**——字体不是变量，数据才是。

**复现与复算**：本地把全部行状态改成「待转移」→ 修复前 **63px**（与 runner 的 64 吻合）；
用纯函数 `fit_columns(needs=[84,259,286,57], minimums=[84,90,90,57], …)` 复算同为 **63**，
修复后为 **90**。

**修法（不删测试，而是让实现真的兜住下限）**：

1. `docmover/ui/main_window.py::_column_widths`：保护列（名称 / 状态）的下限由
   `needs[key]` 改为 `max(needs[key], px(MIN_COL))`——**内容需要宽度**与**文本列硬
   下限**两者取大。这样即使这批数据里没有长状态文案，状态列也不会退化成 63px 的窄列，
   仍留得下「一行可读文本」（后续执行期出现「将合并…」「处理中…」等长文案时也不至于
   把列挤到要重排）。
2. `tests/test_ui_smoke.py::test_status_column_fits_labels`：下限改用
   `column_rules.MIN_COL`（不再写字面量 90），并在断言消息里带上**环境快照**
   （`font` / `scale` / `viewport` / 各列宽 / `need`）——下次再红能一眼分辨是
   「布局算错」还是「数据不同」。
3. `docmover/ui/columns.py`：补注 `保护` 语义（不低于 need **且**不低于 `MIN_COL`）。

**影响面**：名称列在本机由 84px → 90px（+6px，硬下限生效），路径列相应回让，
**各列之和仍恰为可用宽**（`sum == viewport` 契约不变）；离线纯函数测试
`tests/test_columns.py` 自己传 `minimums`，不受影响。

**验证**：本地 `Ran 329 tests OK`，门禁 **8 项全 [OK]**；推送后 **CI 转绿**
（run `38854227223`，`gate in 1m57s`，`Ran 329 tests in 105.110s OK`，
`== 结论：[OK] 全部通过 ==`）。

**产物**：只改 `docmover/ui/` 与 `tests/`，**不进 exe**，**未重打包**。

**结论：唯一剩余的红色用例已修复；契约由「标定出来的绝对像素」回归为「与数据无关」的
相对契约（`max(内容需要宽度, 文本列硬下限)`）。**
