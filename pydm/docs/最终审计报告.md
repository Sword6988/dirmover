## 1. 摘要

### 1.1 一句话结论

这是一个**成熟度显著高于同类工具**的实现：核心数据安全模型（复制 → 源↔目标全量
对照 → 写注册表 → 校验通过才删源）经**逐条实测核验全部成立**；8 项门禁与 317 条
测试全绿；交付产物与源码**字节码级同源**。**没有发现会导致静默数据丢失的缺陷。**

唯一一处需要优先处理的是**纵深防御的时序缺口**：目标祖先链的「重解析点」检查
只在**规划期**执行，执行期不再复查，规划→执行之间的时间窗（可达分钟级）内插入
一个目录联接即可重定向写入并随后删源。该缺口已用端到端脚本**实测复现**
（§3.1 P1-1），修法约 10 行。

## 3. 问题清单

### 3.1 P1 —— 严重（1 项）

#### P1-1　目标**祖先链**的重解析点检查只在规划期，执行期存在 TOCTOU 缺口

**位置**

- `docmover/transfer.py:824`　`validate_destination(target, [current])` ← **唯一的祖先链检查，在规划期**
- `docmover/transfer.py:1033`　`ensure_directory(dirname(item.target))` ← 执行期，直接建父目录（跟随链接）
- `docmover/transfer.py:1046`　`try_atomic_move(...)` ← 执行期，无复查
- `docmover/fsops.py:894`　`if is_reparse_point(dst)` ← **只查目标自身**，不含祖先
- `docmover/fsops.py:923`　`if is_reparse_point(target_dir)` ← 只查 `tree.dirs` 里的**子目录**
- `docmover/fsops.py:1268-1281`　`try_atomic_move` ← 只查 `os.path.exists(dst)`

**问题**

`validate_destination` 里那段「逐级向上检查每一级已存在目录是否重解析点」的闸门
（`fsops.py:414-424`）是审计 F1 的核心修复，其注释明确写着攻击模型：

> 攻击者用 `mklink /J`（**不需要管理员**）把目标指向任意目录，本工具就会以管理员
> 权限写数据、写注册表并删源，界面还报"转移成功"。

但该闸门**只在规划阶段被调用一次**。执行阶段的 `copy_merge` 只检查目标**自身**
与**子目录**，`try_atomic_move` 只检查目标是否存在；两者都**不复查祖先链**。而
`build_plan(..., scan=True)`（`main_window.py:1032-1034`）要为每个文件夹
`scan_tree` 全量枚举——48.7 万文件的真实规模下这是**分钟级**的时间窗。

因此：**规划通过 → 攻击者在目标上级插入 `D:\UserData` → `mklink /J` 到任意目录
→ 执行，数据被写进链接指向的位置，源目录随后被删除。**

**实测复现（已证实，非推测）**

脚本：`D:\tmp\toctou_probe.py`（用 `tempfile` 造目录，不碰真实用户文件夹）

```
[规划期] validate_destination -> True
[规划后] 攻击者建 junction: ...\UserData -> ...\real_root   建链成功: True
[执行期] copy_merge(src, target)
         ok = True  errors = []
         数据是否落进 junction 指向的真实目录 ? True        ← 数据被重定向
场景二：try_atomic_move(...) -> True 已通过原子重命名完成转移
         源是否已被移走? True                              ← 整个文件夹被搬进链接目标
         数据是否落进 junction 目标 ? True
```

关键点：`copy_merge` 返回 **`ok=True`、`errors=[]`**，即**没有任何信号**提示异常；
后续 `_execute_item` 的两道删源前闸门（`resolves_to_same`、二次枚举指纹比对）也
都**不会**命中——因为源与目标物理位置确实不同、源树自身也没有变化。源目录照删。

**影响（用户可见后果）**

用户「文档 / 桌面 / 下载」等目录的数据被移动到攻击者指定的位置，**源目录被删除**，
注册表指向的逻辑路径在链接被移除后变成空路径。从用户视角等同于**数据丢失**；
且该工具以管理员权限运行，杀伤面覆盖整个目标盘。

**前置条件（如实标注，不夸大）**

需要目标盘上存在一个能在时间窗内创建目录的本地进程（低权即可，`mklink /J` 不需要
管理员）。单用户离线环境风险有限；但这是一个**纯本地、无交互、可自动化**的攻击面，
且与项目自己在 F1 里确立的威胁模型完全一致，故定级 P1。

**最小修法**

1. 把 `fsops.validate_destination:414-424` 的祖先链检查抽成独立纯函数，例如
   `fsops.assert_no_reparse_ancestor(path) -> Tuple[bool, str]`（沿用现有 `probe` 上溯逻辑）。
2. 在**执行期**再调用一次：
   - `transfer._execute_item` 中，`fsops.ensure_directory(...)`（`transfer.py:1033`）**之前**；
   - `fsops.try_atomic_move` 开头（`fsops.py:1270` 附近）；
   - 或直接在 `copy_merge` 开头（`fsops.py:894` 处）把「只查 dst 自身」扩成「查 dst 及祖先链」。
     这一条是**纵深防御**口径，与现有 F1 修复同源，改动最小（把 `probe` 上溯循环搬过去）。
3. 补端到端回归：规划（`build_plan`）→ 在目标上级建 junction → `execute` →
   断言**该项失败且源目录保留**、目标盘无写入。
4. 同步 README 的「转移流程（安全模型）」：把「目标不为空、是绝对路径…」那条补上
   「**目标及其每一级已存在上级都不得是链接/联接点**（执行期与规划期各查一次）」。

**置信度：已证实**（端到端实测 + 逐行读码交叉确认）

### 3.2 P2 —— 一般（2 项）

#### P2-1　README「不会停在删除中途」的承诺强于实现（60 秒强制退出）

**位置**

- `docmover/ui/main_window.py:71`　`_EXIT_TIMEOUT_MS = 60000`
- `docmover/ui/main_window.py:1518-1541`　`_poll_exit`：等待超时后 `self.root.destroy()`
- `README.md:168-169`（「转移流程」第 3 点）：「…等当前项写完并校验后再退出，**不会停在删除中途**」

**问题**

`_on_exit` → `_poll_exit` 的收尾设计是正确的（置取消位 → 轮询等 `_busy`/`_finishing_ui`
→ 再销毁），但它有一个 **60 秒兜底**：超时即 `destroy()`，`mainloop` 返回后
`run.py` 走到 `finally`，daemon 工作线程被进程退出强杀。若此刻线程正在
`fsops.safe_remove_directory` 的 `shutil.rmtree` 里（数十万文件的大目录完全可能
超过 60 秒），就会**停在删源中途**——与 README 的绝对化承诺不符。

**影响**：数据不丢（内容已完整复制并通过校验，且注册表已正确写入），但源目录会
剩下「删了一半」的残骸，用户看到的状态与文档承诺不一致。

**最小修法**：二选一——
(a) 把 README 那句改成如实口径：「极端情况下最多等待 60 秒，之后程序会强制退出
（此时数据已复制并校验完成，仅源目录可能残留部分文件，可手动删除）」；
(b) 或让 `_poll_exit` 在超时后**不销毁**而是提示用户「正在删除源目录，请稍候」，
并把超时改为「至少等到删源阶段结束」。

**置信度：高**（读码确定；未构造 60 秒以上的真实删除来实测，因为不值得在真实磁盘上触发）

#### P2-2　「重启资源管理器」在交付产物中恒不生效，但界面每次仍会询问

**位置**

- `docmover/shell.py:77-105`　`is_autorestart_shell_enabled` 读 **HKCU** 下 `AutoRestartShell`
- 该值实际位于 **HKLM** → 实测恒返回 `False`
- `docmover/shell.py:230-234`　`restart_explorer` 因此恒走「已跳过重启」分支
- `docmover/ui/main_window.py:1142`　`_confirm_restart_explorer`（转移成功后仍会询问）

**问题**：功能不可达是**已知并有意保留**的（审计报告 §8.14.2「事实二」已记档为
「已上膛、保险未开」，并明确决策「不改可达性」）。但站在**最终交付**的立场，
这仍是一处**用户可见的功能缺口**：用户每次转移成功后都会看到「是否重启资源管理器」
的询问，点「是」却只会得到「系统未启用 shell 自动重启…已跳过重启」。用户会以为
功能坏了——因为它确实没生效。

**影响**：不涉及数据安全；属产品体验与承诺一致性问题。

**最小修法**（需产品决策，三选一）：
(a) 保持不改可达性，但在界面与 README 中把该入口明确改为「**注销后重新登录生效**」
的说明，并**不再询问**是否重启（消除"点了没用"的落差）；
(b) 修 `is_autorestart_shell_enabled` 读取 hive（HKLM）使其真正生效——**必须先单独
评审「是否应该强杀 explorer」**，因为一旦可达就会对用户的资源管理器执行 `/f`；
(c) 维持现状，但在交付说明中显式告知用户该能力当前不生效。

**置信度：已证实**（函数 docstring 自述 + 读码交叉确认；本轮未实际执行强杀以验证）

> **现状更新（2026-10-16，见 `审计报告.md` §8.19）**：已按上述 **(b)** 落地。
> 只读实测补充了关键证据：`HKLM\...\Winlogon\AutoRestartShell` **= 1**，
> `HKCU\...\Winlogon` **存在但无该值**。据此更正本节的定性：这不是「有意保留的
> 保守取舍」，而是**读错 hive 的缺陷**。`§8.14.2 事实二` 与 README 旧「已知边界」里
> "刻意保守"的说法应作废。同时修掉了伴随问题：
> `restart_explorer` 原先"强杀按用户过滤、列举不过滤"，在多头登录机器上会误判
> 恢复状态；现已统一。**该改动是行为变更**：默认系统上点「是」会真正重启 explorer。

## 4. 已排除项与正面确认（证据）

### 4.1 一个 P0 级假设被实测证伪

**假设**：「源目录内含目录联接（junction）时，收尾的 `shutil.rmtree` 会跟随链接，
删掉链接**指向**的目录内容。」

**实测**：在临时目录里建 `src\link -> victim`，`victim` 内放 2 个文件，调用
`fsops.safe_remove_directory(src)`。结果：`src` 被删除、**`victim` 及全部文件完好**。

**机理**：Python 3.14 的 `_rmtree_unsafe` 用
`os.walk(..., followlinks=os._walk_symlinks_as_files)`，联接点被当作文件处理
（unlink 链接本身，不递归）。

先写注册表、`:1223` 才删源，与 README 承诺一致。
